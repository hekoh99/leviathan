Final system blueprint · v1.0 · FROZEN

LEVIATHAN

Local-first, goal-driven, LLM-guided modular trading platform.

Leviathan은 사용자가 입력한 목표 금액·기간·허용 리스크를 바탕으로 목표 실현가능성을 정량 평가하고, 시장 데이터·뉴스·재무정보를 분석해 투자 후보와 전략 신호를 생성하며, 결정론적 포트폴리오·리스크·실행 엔진을 통해 paper trading에서 실제 자동매매까지 단계적으로 확장하는 개인용 Linux CLI 트레이딩 시스템이다.

최종 설계 원칙: LLM은 사실을 해석하고 후보·conviction·전략 신호를 제안한다. 최종 숫자 비중, 리스크 한도, 주문 허용 여부, 체결 상태, 회계는 deterministic code가 결정한다. LLM은 브로커 API에 직접 접근하지 않는다.

Goal-driven

목표 CAGR과 도달 확률을 계산하고, 목표 진행상황을 지속적으로 재평가한다.

Agentic, not unbounded

LLM은 매 사이클 새 정보를 해석하지만 실행 가능한 출력은 제한된 schema와 검증 단계를 통과한다.

Paper → Live

초기 PaperBroker는 첫 실행 환경일 뿐이며, 최종적으로 실제 증권사 어댑터와 live execution을 지원한다.

Replaceable modules

Broker, model provider, data provider, strategy, portfolio constructor를 서로 독립적으로 교체할 수 있게 한다.

2. 설계 원칙

CORELLM ≠ 계산 엔진

LLM은 의미 해석, 뉴스 연결, thesis, 후보 순위와 conviction을 제공한다. 제약식과 최종 비중 계산은 코드가 담당한다.

SAFETYFail closed

데이터가 stale하거나 모델 호출이 실패하거나 검증을 통과하지 못하면 신규 거래를 하지 않는다. 기본 fallback은 HOLD다.

DESIGNPoint-in-time first

모든 판단은 그 순간 이용 가능했던 데이터 snapshot과 revision 정보를 기준으로 재현 가능해야 한다.

COREBroker-independent core

Strategy, Portfolio, Risk는 KIS/Hana를 모른다. broker-specific 인증·주문 포맷은 adapter 내부에만 존재한다.

COREIntelligence service is stateless

Python intelligence service는 상태를 소유하지 않는다. Request → compute → Response만 수행하며 DB에 쓰지 않고 broker를 호출하지 않는다.

5. LLM 신호와 결정론적 숫자의 분리

LLM이 target_weight: 0.123 같은 최종 숫자를 직접 만드는 구조는 사용하지 않는다. LLM은 제한된 범위의 신호만 반환한다. 

{
  "market_regime": "risk_on",
  "candidates": [
    {
      "symbol": "005930",
      "conviction": 4,
      "suggested_weight_band": [0.05, 0.12],
      "horizon_days": 20,
      "thesis": "...",
      "key_risks": ["..."]
    }
  ],
  "cash_weight_hint": [0.15, 0.25],
  "confidence": 0.71
}

Portfolio Constructor가 conviction, weight band, 변동성, 상관관계, 현재 risk budget을 받아 최종 비중을 계산한다. 첫 버전은 conviction 비례 또는 inverse-volatility 정도의 단순한 방식으로 시작한다.

같은 signal input과 같은 market snapshot이면 언제나 같은 portfolio target이 생성되어야 한다. “왜 12.3%인가?”에 대한 답은 LLM 설명이 아니라 코드와 입력값으로 재현할 수 있어야 한다.

7. Goal Feasibility & Progress-Adaptive Risk Budget

7.1 Goal Feasibility Engine

요구 CAGR은 코드로 계산하고, Monte Carlo 또는 명시적 확률 모델로 목표 기간 내 도달 가능성을 추정한다. LLM은 이 확률을 직접 만들지 않고 결과를 설명하고 대안을 제시한다. 

required_cagr = (target / initial)^(365 / days) - 1

Inputs:
- initial capital
- target value
- target date
- risk profile
- historical / assumed return distribution

Outputs:
- required CAGR
- success probability by risk profile
- expected drawdown range
- alternative target / period scenarios

7.2 Glide Path & Risk Budget Controller

목표 시작 시점부터 target date까지 기대 NAV glide path를 만들고 실제 NAV와의 편차를 계산한다. Risk Budget Controller는 사전 승인된 envelope 안에서만 리스크 파라미터를 조정한다.

  • 목표를 앞서가면: cash floor를 높이고 position cap을 낮춰 이익 보존.
  • 약간 뒤처지면: 승인된 범위 안에서만 소폭 risk budget 확대.
  • 크게 뒤처지고 시간이 부족하면: 리스크를 무제한 키우지 않고 목표/기간 재설정을 사용자에게 제안.
Leviathan은 “목표가 멀어졌으니 더 큰 베팅을 해서 따라잡는다”는 추격매매를 자동화하지 않는다. Risk envelope 밖의 확대는 코드가 거부한다.

9. Grounding & Validation

LLM 결과는 주문 경로에 들어가기 전에 최소 세 종류의 검증을 거친다.

Schema

Pydantic/Serde schema를 만족하지 못하면 retry 후 HOLD.

Entity

언급 종목이 실제 candidate universe와 instrument master에 존재하는지 검사.

Fact

PER, 가격, 거래량 같은 수치가 supplied context에서 추적 가능한지 검사.

LLM self-critique는 보조 수단일 뿐이며 최종 grounding 판단은 가능한 범위에서 deterministic validation을 우선한다.

11. Portfolio / Accounting / Ledger

Rust core가 source of truth 역할을 한다.

  • cash / reserved cash
  • positions / lots / average cost
  • realized & unrealized P&L
  • orders / fills / fees / taxes where modeled
  • NAV / exposure / turnover / drawdown
  • broker reconciliation state

모든 상태 변경은 replay 가능한 event 또는 append-oriented ledger record로 남겨, 프로세스 재시작 후에도 portfolio state를 재구축할 수 있게 한다.

12. 평가 전략: Forward-first

범용 LLM은 과거 시점 이후의 정보를 학습 파라미터에 포함하고 있을 수 있다. 따라서 “2024년 시점이라고 가정해 판단하라”는 식의 LLM 역사 백테스트 결과를 성능 증거로 사용하지 않는다.

평가를 세 가지로 분리한다.

  1. Deterministic historical replay: LLM 대신 stand-in 규칙 전략을 넣어 데이터→회계→리스크→체결→리포트 파이프라인 검증.
  2. Forward paper trading: 실제 시점의 데이터만으로 LLM 의사결정 품질을 평가하는 1차 성과 검증.
  3. Offline prompt eval: 이미 저장된 forward decision context를 새 prompt/model에 재입력해 parse, cost, consistency, ranking 변화 등을 비교.

성과 지표:

Total return Benchmark return Alpha Max drawdown Volatility Sharpe-like Turnover Hit rate LLM cost Parse failure

13. Storage Architecture — SQLite First

Leviathan의 초기 및 중기 운영 저장소는 SQLite 하나로 통합한다. 이 선택은 단순함 때문만이 아니라, 현재 아키텍처의 실제 workload와 일관성 요구에 잘 맞기 때문이다.

13.1 왜 SQLite 하나로 충분한가

  • Single-writer 구조: Rust 프로세스가 trading cycle을 소유하고 Python worker의 결과를 받아 순차적으로 상태를 기록한다. 따라서 SQLite의 대표적 약점인 높은 동시 write 경합이 현재 설계에서는 거의 발생하지 않는다.
  • 재현 가능성: decision, market snapshot metadata, screening result, risk decision, order/fill을 하나의 transactional store에 두면 동일한 snapshot semantics와 reference chain을 유지하기 쉽다. 저장소를 여러 개로 나누면 cross-store consistency와 snapshot coordination을 애플리케이션이 직접 책임져야 한다.
  • 운영 단순성: 서버 프로세스, 네트워크 인증, 별도 DB 운영 없이 로컬 파일 하나로 상태를 관리할 수 있다.
  • 백업 단위 단순화: operational state의 source of truth가 하나이므로 일관된 snapshot을 만들고 복구하는 절차가 단순하다.
SQLite를 쓰는 이유는 “데이터가 적어서”가 아니라, local-first + single-writer + low-concurrency + strong reproducibility라는 Leviathan의 구조와 잘 맞기 때문이다.

13.2 하나의 DB, 세 가지 논리적 데이터 그룹

그룹예시보존 정책
Core Ledger orders, fills, positions, portfolio_snapshots, goals, llm_decisions, risk_decisions 영구 보존. 실제 실행 기록이므로 재생성 불가.
Reproducibility Evidence decision market snapshots, screening_results, grounding_checks, prompt_versions 장기 보존. 당시 판단을 재현하는 근거.
Cache / Dev Data 재수집 가능한 price cache, news metadata cache, eval_runs, temporary analysis 필요 시 prune 가능.

특히 재수집 가능한 일반 market cache와 실제 decision에 사용된 market snapshot은 구분한다. 후자는 cache가 아니라 audit evidence이므로 삭제하지 않는다.

13.3 큰 텍스트·아티팩트는 파일시스템으로 분리

구조화된 메타데이터와 join 대상은 SQLite에 두되, SQL query에 직접 필요하지 않은 큰 원문은 파일시스템에 저장한다.

데이터저장 위치
뉴스 기사 원문 filesystem (data/news/)
LLM에 전달한 전체 context snapshot filesystem (data/contexts/)
HTML / Markdown report filesystem (reports/)
경로, hash, timestamp, source, summary, decision reference SQLite

분리의 주된 이유는 “큰 텍스트는 DB에 저장할 수 없어서”가 아니다. raw artifact는 압축·diff·직접 열람·중복 제거가 쉽고, operational DB는 빠른 join과 상태 관리에 집중할 수 있기 때문이다. 

data/
├─ leviathan.db
├─ artifacts/
│  └─ sha256/
│     └─ ab/
│        └─ abcdef....json.zst
├─ news/
├─ contexts/
└─ reports/

가능한 경우 artifact는 content hash 기반으로 저장한다. DB에는 hash, relative_path, media_type, size_bytes, created_at만 기록한다. 동일 context를 여러 eval run에서 재사용해도 중복 저장하지 않는다.

13.4 Trading Cycle은 “긴 하나의 트랜잭션”이 아니다

research → LLM → risk → execution 전체 동안 DB transaction을 열어두지 않는다. 외부 API나 LLM 호출은 수 초가 걸릴 수 있으므로, 각 단계는 짧은 transaction으로 commit하고 전체 cycle은 recoverable state machine으로 관리한다. 

cycle_id = 123

CREATED
  ↓
RESEARCH_SNAPSHOT_COMMITTED
  ↓
DECISION_COMMITTED
  ↓
PORTFOLIO_TARGET_COMMITTED
  ↓
RISK_APPROVED
  ↓
ORDER_INTENT_COMMITTED
  ↓
EXECUTED / REJECTED / HALTED

프로세스가 중간에 죽어도 cycle_id와 상태를 통해 어디까지 완료됐는지 알 수 있어야 하며, live trading에서는 idempotency key를 사용해 같은 주문이 두 번 생성되지 않도록 한다.

13.5 초기 SQLite 설정

PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
  • WAL: trading loop가 쓰는 동안 CLI/report reader가 조회할 수 있게 한다.
  • foreign_keys: schema 관계를 실제로 강제한다.
  • busy_timeout: 짧은 lock 충돌에서 즉시 실패하는 것을 줄인다.

sqlx migrate로 schema version을 관리하고, 애플리케이션 시작 시 필요한 PRAGMA가 실제 connection에 적용됐는지 검증한다.

13.6 백업

실행 중인 WAL database를 단순히 cp leviathan.db로 복사하는 방식을 live backup으로 사용하지 않는다. SQLite Online Backup API 또는 CLI의 .backup을 사용한다. 

sqlite3 leviathan.db ".backup backups/leviathan-2026-08-09.db"

Core Ledger는 재생성할 수 없는 유일한 실행 기록이므로, live trading 단계에서는 자동 일일 backup과 일정 개수의 rolling retention을 기본 운영 정책으로 둔다. Artifact Referential Integrity: DB에서 하나 이상의 persistent record가 참조하는 artifact는 삭제할 수 없다. Artifact GC는 DB에서 참조되지 않는 object만 대상으로 하며, backup/restore 및 정기 integrity verification 시 파일 존재 여부와 content hash를 검증한다.

13.8 언제 SQLite를 벗어나는가

DB 교체는 선제적으로 하지 않고 실제 workload가 필요성을 증명할 때 진행한다.

  • 여러 독립 프로세스가 지속적으로 동시에 write하기 시작할 때.
  • 틱 단위 또는 대규모 분봉 데이터를 장기간 저장해 analytical scan이 커질 때.
  • 여러 기기/원격 환경에서 동일 DB에 접근해야 할 때.
  • 대규모 research query가 operational trading query의 latency를 방해하기 시작할 때.

마지막 경우에는 operational DB 전체를 즉시 PostgreSQL로 옮기기보다, 먼저 SQLite = operational / DuckDB+Parquet = analytical 형태로 분리하는 것을 우선 고려한다. 

Stage 1~N
SQLite
└─ operational + moderate market data

If analytical workload grows:
SQLite
└─ ledger / decisions / orders / live state

DuckDB + Parquet
└─ bulk history / factor research / large scans

If concurrency/distribution grows:
PostgreSQL
└─ operational store replacement
Migration principle: storage access는 repository boundary 뒤에 숨긴다. 초기에는 SQLite implementation만 제공하고, 실제 필요가 생길 때 analytical store 또는 PostgreSQL implementation을 추가한다. 데이터베이스 선택이 core trading domain을 오염시키지 않게 한다.

14.2 Schema Ownership — Rust가 단일 source of truth

Intelligence service가 주고받는 모든 request/response 타입은 leviathan-contracts에서 먼저 정의한다. leviathan-domain의 내부 도메인 타입을 그대로 서비스 계약으로 노출하지 않는다. Python 쪽 Pydantic 모델은 손으로 작성하지 않고 contracts DTO에서 생성된 산출물이다. 

leviathan-contracts DTO (Rust + schemars derive)
      │  cargo xtask schema-gen
      ▼
schemas/generated/*.schema.json
      │  datamodel-code-generator
      ▼
intelligence/src/leviathan_ai/schemas/generated/*.py  (Pydantic)

이 파이프라인은 CI에서 검증한다 — codegen을 다시 돌렸을 때 diff가 발생하면 (Python 쪽 스키마가 손으로 수정되었거나 재생성을 누락했다는 뜻이므로) 빌드를 실패시킨다. 스키마 불일치는 리뷰가 아니라 빌드가 잡는다.

14.3 Service Boundary — Rust ↔ Python

Intelligence service는 상태를 소유하지 않는다. 매 호출은 Request → compute → Response 한 사이클로 끝나며, DB에 쓰지 않고 broker를 호출하지 않으며 portfolio나 order를 직접 갱신하지 않는다. FastAPI로 구현한다고 해서 이 서비스가 trading system의 상태를 독립적으로 소유하는 microservice가 되는 것은 아니다 — core가 매 사이클 호출하는 순수 계산 함수의 집합일 뿐이다.

외부에 노출하는 API는 제품 수준의 작업 단위로만 구성한다. news processing, regime, ranking, grounding, conviction 같은 내부 파이프라인 단계를 각각 별도 엔드포인트로 쪼개 노출하지 않는다 — 그렇게 하면 Rust가 그 순서대로 호출해야 하므로 Python의 내부 LLM 파이프라인 구조를 알게 되고, 파이프라인이 바뀔 때마다 Rust 쪽 호출 순서도 같이 바뀌어야 한다. 

외부 API (Rust가 아는 전부)
intelligence/src/leviathan_ai/api/
├─ analyze_cycle.py       POST /analyze-cycle
├─ explain_goal.py        POST /explain-goal
├─ generate_report.py     POST /generate-report
└─ health.py              GET  /health

내부 파이프라인 (Rust는 모름, model_router/가 조율)
analyze_cycle
   ↓
news processing        cheap
   ↓
regime                 mid
   ↓
ranking                mid
   ↓
strong model            strong  (conviction / weight band)
   ↓
grounding
   ↓
response

8장 Model Routing 표의 태스크들은 더 이상 개별 라우트가 아니라, model_router/가 analyze_cycle 한 번의 호출 안에서 순서대로 조율하는 내부 단계다. Rust는 어떤 모델을 몇 단계 거쳐 이 결과가 나왔는지 알 필요가 없고, 알아서도 안 된다 — 알게 되는 순간 Rust core가 Python의 내부 구현에 의존하게 된다. explain_goal도 같은 원칙을 따른다. required CAGR, Monte Carlo 결과, glide path와 같은 수치적 결과는 leviathan-goal이 계산한 값을 request로 전달하며, Python은 이를 다시 계산하지 않는다. Intelligence service는 해당 결과의 설명·대안 narration만 생성해 반환한다.

Uvicorn은 TCP 포트가 아니라 Unix domain socket에 바인딩한다 (uvicorn --uds /run/leviathan/intelligence.sock). 로컬 프로세스 간 통신만 필요하므로 네트워크 attack surface를 아예 만들지 않는다. analyze_cycle의 request body가 그대로 research_contexts에 저장되는 artifact이므로, Eval Harness는 저장된 request를 다시 analyze_cycle에 재전송하는 것만으로 offline 재현을 수행한다 — 내부 파이프라인 단계를 개별적으로 재생할 필요가 없다.

14.4 Stateless 원칙의 강제 — 코드 리뷰가 아니라 구조로

"Python이 DB/Broker를 직접 건드리지 않는다"는 관례가 아니라 세 겹으로 강제한다.

프로세스 격리

leviathan.db 경로와 broker credential은 intelligence 프로세스의 env var/config 어디에도 전달되지 않는다.

API 표면 설계

모든 외부 API는 "분석해줘" 의미만 갖는다. "이걸 써줘/주문해줘" 같은 쓰기 의미의 엔드포인트는 설계상 존재하지 않는다.

CI guard

intelligence/ 안에서 DB 드라이버·broker SDK import를 감지하면 빌드를 실패시키는 lint를 둔다.

메모리 내 caching(warm model client, embedding cache 등)은 예외로 허용한다 — trading system의 authoritative state가 아니라 순수 성능 최적화이기 때문이다.

16. Scheduler / Decision Cadence

자동 실행 주기는 단순한 운영 옵션이 아니라 전략 정의의 일부다. 판단 주기는 LLM 호출 비용, 데이터 신선도, 거래 빈도, turnover, glide path 평가 빈도에 모두 영향을 준다. 따라서 각 run은 생성 시 명시적인 cadence policy를 가진다.

16.1 기본 원칙

  • v1의 기본은 low-frequency다. HFT나 tick-driven execution은 목표로 하지 않는다.
  • Research/decision cadence와 execution/rebalance cadence를 분리할 수 있다.
  • Goal glide path는 일 단위 기준점을 갖고, intraday cycle마다 무의미하게 목표 편차를 다시 해석하지 않는다.
  • 동일 run의 동일 scheduled slot은 한 번만 실행되도록 idempotent cycle key를 사용한다.
  • 시장 휴장일, 조기 폐장, 데이터 미수신 시에는 거래 대신 명시적 SKIPPED 상태를 기록한다.

16.2 권장 초기 cadence

Daily
├─ pre-market research cycle     1회
├─ market-open execution         필요 시 1회
├─ optional midday risk check    0~1회
└─ end-of-day evaluation         1회

Weekly
└─ strategic portfolio review

Monthly
└─ goal feasibility + glide path re-evaluation

초기 paper 단계에서는 하루 1회의 full LLM decision cycle부터 시작하고, 성능·비용·데이터 품질을 확인한 뒤 필요한 경우에만 intraday cycle을 추가한다.

16.3 Cadence Configuration

[schedule]
timezone = "Asia/Seoul"
decision = "daily"
decision_time = "08:40"
rebalance = "daily"
evaluation_time = "16:10"

[strategy_review]
frequency = "weekly"

[goal_review]

실제 broker 시장 시간은 market calendar abstraction을 통해 계산하고, cron 문자열만으로 시장 개장 여부를 추정하지 않는다.

16.4 Cost와 cadence의 연결

ModelRouter는 호출 건별 비용을 기록하고 scheduler는 run별 호출 횟수를 예측한다. 계획 단계에서 예상 월간 LLM 비용을 함께 보여주며, cadence 변경 시 예상 비용도 재계산한다. 

estimated_monthly_llm_cost
=
scheduled_cycles_per_month
× expected_calls_per_cycle
× expected_cost_per_call
초기 권장: full decision cycle은 하루 1회. 뉴스 수집·정량 필터는 더 자주 돌아도 되지만, expensive model을 매번 호출할 필요는 없다.

17. 운영 안정성 / 보안 / 재해복구

  • LLM failure: timeout + bounded retry + exponential backoff → HOLD.
  • LLM cost circuit breaker: run별/일별 API spend ceiling과 호출 횟수 상한을 둔다. soft limit 도달 시 경고, hard limit 도달 시 expensive LLM 호출을 중단하고 HOLD 또는 deterministic fallback으로 전환한다.
  • Data staleness: freshness threshold 초과 시 cycle skip.
  • Idempotency: 모든 live OrderIntent에 unique key를 부여해 재시작/timeout 시 중복 주문 방지.
  • Partial fill: fill 단위로 ledger 반영, target과 실제 position 차이를 재계산.
  • Reconciliation: broker positions/orders/fills와 local state 불일치 시 자동매매 중단.
  • Kill switch: paper 단계부터 구현하고 live에서는 신규 주문 차단 + 상태 snapshot 저장.
  • Secrets: API key는 repository에 저장하지 않고 OS keyring 또는 제한된 local secret store 사용.
  • Logging: broker credential과 token은 마스킹하고 decision/order audit trail은 보존.
  • LLM isolation: intelligence process에는 broker credential과 DB 파일 경로를 전달하지 않는다 (14.4 참고).
  • Automated backup: Phase 1부터 SQLite Online Backup API/.backup을 사용해 정기 snapshot을 생성한다.
  • Off-disk copy: 같은 디스크의 backup만으로는 재해복구가 되지 않으므로, live 전에는 최소 하나의 별도 물리 매체 또는 암호화된 원격 저장 위치에 backup을 복제한다.
  • Artifact backup: DB가 참조하는 immutable context/news artifacts도 DB backup과 함께 backup generation ID를 기준으로 보존한다.
  • Restore drill: backup이 존재하는 것만 확인하지 않고, 정기적으로 새 디렉터리에 복원해 ledger replay와 artifact hash 검증이 성공하는지 테스트한다.

각 backup generation에는 DB snapshot 시각과 필요한 artifact hash 목록을 manifest로 남긴다. 복구 성공 기준은 단순히 DB 파일이 열리는 것이 아니라, cycle → decision → evidence → order/fill reference chain을 재구성할 수 있는 것이다.

Core Ledger가 source of truth라면 백업은 운영 부가 기능이 아니라 correctness의 일부다. 따라서 backup job과 restore test는 Phase 1부터 개발 환경에서도 실행한다.

18. Multi-Run / Account Allocation

하나의 Leviathan 프로세스에서 여러 run을 동시에 운영할 수 있지만, live trading에서 두 run이 동일 broker account를 공유할 경우 cash와 exposure ownership을 명시적으로 정의해야 한다.

18.1 기본 정책

초기 live 버전에서는 단순성과 안전성을 위해 1 live run = 1 account allocation을 기본으로 한다. 다만 실제 broker account 자체를 run마다 새로 만들 필요는 없으며, 하나의 실계좌 안에서 Leviathan이 관리하는 virtual allocation을 둘 수 있다. 

Broker Account
├─ account cash
├─ external/manual positions
└─ Leviathan allocations
   ├─ allocation A → run-001
   └─ allocation B → run-002

18.2 Account-level Risk가 최종 권위

run별 virtual cash가 충분해 보여도 실제 계좌 전체의 available cash와 exposure가 부족하면 주문할 수 없다. 따라서 두 단계 검사를 수행한다. 

Run-level check
├─ allocated_cash
├─ run reserved_cash
├─ run position limits
└─ run drawdown

        ↓ pass

Account-level check
├─ broker available_cash
├─ total reserved_cash across runs
├─ total account exposure
├─ external/manual positions
└─ account-wide hard limits

        ↓ pass

OrderIntent

reserved_cash는 물리적으로 account-level reservation ledger에서 관리하고 각 reservation이 run_id 또는 allocation_id를 소유하도록 한다. 이렇게 해야 두 run이 같은 현금을 동시에 쓸 수 없다.

18.3 초기 구현 범위

  • Paper 단계: 여러 run 허용, 각 run에 독립 virtual account 사용.
  • Assisted Live 초기: 하나의 broker account에 하나의 active live allocation만 허용해 복잡성을 제한.
  • Multi-run live가 필요해질 때: account_allocations, cash_reservations, account-level risk ledger 추가.
  • 사용자가 broker 앱에서 수동 거래한 포지션도 reconciliation 시 account-level exposure에 포함.
이 설계는 지금 당장 multi-run live를 구현하겠다는 뜻이 아니라, reserved cash의 최종 소유권은 run이 아니라 실제 account라는 invariant를 미리 확정하는 것이다.

19. 테스트 전략

  • Property-based accounting tests: cash + position value = NAV, fill conservation, no impossible balances.
  • Risk boundary tests: 한도 직전/직후, envelope transition, drawdown halt.
  • Broker contract tests: Paper/KIS/Hana adapter가 동일한 Broker semantics를 만족하는지 검증.
  • Execution failure tests: timeout, duplicate response, rejected order, partial fill, restart.
  • Cycle recovery tests: 각 state transition 직후 crash를 가정하고 재시작 시 중복 없이 이어지는지 검증.
  • SQLite integration tests: WAL/read concurrency, FK violation, busy timeout, migration, backup/restore 검증.
  • Scheduler tests: market holiday, timezone/DST, duplicate scheduled slot, missed cycle recovery.
  • LLM budget tests: retry storm과 hard spend limit 도달 시 추가 호출이 차단되는지 검증.
  • Account allocation tests: 두 run이 동일 cash를 동시에 reserve하지 못하는지 검증.
  • Disaster recovery drill: DB + artifact backup에서 새 환경으로 restore 후 ledger replay 검증.
  • LLM schema tests: malformed JSON, invalid symbol, unsupported fact, retry/HOLD fallback.
  • Historical deterministic replay: stand-in strategy로 전체 pipeline regression.
  • Forward paper eval: 실제 decision performance와 benchmark 비교.
  • Prompt regression eval: 동일 저장 context에 대해 model/prompt 버전별 parse/cost/signal 변화 비교.

21. 성공 기준

Leviathan의 성공은 단순히 “돈을 벌었다”가 아니다.

  • 당시 이용 가능한 정보만으로 모든 decision을 설명·재현할 수 있다.
  • LLM의 실제 기여를 deterministic baseline과 분리해 측정할 수 있다.
  • 같은 신호와 같은 snapshot에서 동일한 portfolio target이 생성된다.
  • LLM이 이상한 결정을 내려도 위험 한도를 넘는 주문은 생성되지 않는다.
  • Paper와 Live가 동일한 core를 사용하고 Broker만 교체된다.
  • 새 broker/model/data provider 추가가 핵심 domain 수정으로 이어지지 않는다.
  • 실계좌와 내부 ledger 차이를 탐지하고 fail-safe 상태로 전환할 수 있다.
  • SQLite backup 하나와 artifact directory만으로 특정 시점의 실행 상태와 판단 근거를 복구할 수 있다.
  • 자동 scheduler가 동일 cycle을 중복 실행하지 않고, cadence와 예상 LLM 비용이 run 설정으로 재현 가능하다.
  • API retry storm이 발생해도 일일 LLM 비용 hard limit을 초과하지 않는다.
  • 복수 run이 동일 실계좌를 공유하더라도 cash reservation과 account-level exposure가 이중 계산되지 않는다.
  • 주기적인 restore drill을 통해 ledger와 evidence chain의 실제 복구 가능성이 검증된다.
  • 장기간 forward history를 통해 전략·모델·비용·리스크를 지속 평가할 수 있다.
